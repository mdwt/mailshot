# Mailshot Desktop — Frontend Design

A desktop control panel for bootstrapped mailshot projects. The app opens a project folder
(created by `create-mailshot`), interprets its sequence configs and `.env`, and provides a
GUI for viewing/editing emails and sequences, managing deployments, and reading stats and
analytics from the user's AWS account.

Guiding principle: **the project folder is the source of truth**. The app is a lens over
files + AWS — it never keeps its own database. Everything the app shows is derived from
`sequences/*/sequence.config.ts`, `build/`, `.env`, and live AWS reads. This keeps it fully
compatible with the Claude Code workflow: the app and Claude Code can work on the same
project simultaneously (file watchers keep the UI in sync).

---

## 1. Core concept

```
┌────────────────────────────────────────────────────────────┐
│  Mailshot Desktop (Wails)                                  │
│                                                            │
│  React frontend  ◄── Wails bindings ──►  Go backend        │
│  (views, canvas,                        (project parsing,  │
│   editors)                               AWS SDK, deploy   │
│                                          process runner)   │
└──────────┬─────────────────────────────────┬───────────────┘
           │                                 │
           ▼                                 ▼
   ~/my-mailshot-project/             AWS account (from .env)
   ├── .env                           ├── DynamoDB (subs, stats, events)
   ├── sequences/*/sequence.config.ts ├── Step Functions (executions)
   ├── sequences/*/src/emails/        ├── S3 (deployed templates)
   └── build/<id>/templates/*.html    ├── CloudFormation (stack)
                                      └── SES (identities, quotas)
```

Three data planes, clearly separated in the UI:

| Plane        | Source                          | Freshness                 |
| ------------ | ------------------------------- | ------------------------- |
| **Local**    | config files, templates, `.env` | live (file watcher)       |
| **Deployed** | CloudFormation, S3, SFN defs    | on demand + after deploy  |
| **Runtime**  | DynamoDB, SFN executions, SES   | polled while view is open |

The Local vs Deployed distinction powers a **drift indicator**: when local configs differ
from what's deployed, the UI shows "undeployed changes" (like a git dirty state) and the
Deploy screen becomes the call to action.

## 2. Architecture

### 2.1 Go backend (Wails-bound services)

One bound struct per concern; all return JSON-serializable DTOs so TypeScript types are
generated by Wails.

**ProjectService**

- `OpenProject(path)` — validates the folder is a mailshot project (has
  `sequences/`, `.env` or `.env.example`, `bin/app.ts`), loads `.env`, returns a
  `Project` DTO. Maintains a recent-projects list (stored in the OS app-data dir —
  the only app-owned state).
- Watches the project with `fsnotify` (sequences/, .env) and emits Wails events
  (`project:changed`, `sequence:changed:<id>`) so views refresh automatically —
  this is what makes "Claude Code edits, app updates live" work.

**SequenceService**

- `ListSequences()` / `GetSequence(id)` — parses each `sequences/<dir>/sequence.config.ts`
  into a JSON `SequenceDefinition`.
- **How TS configs are read from Go**: esbuild is a Go library
  (`github.com/evanw/esbuild/pkg/api`). Bundle the config in-process
  (externalizing `@mailshot/shared`, which is types-only at runtime), then evaluate the
  CJS output with `goja` (pure-Go JS engine) and take `module.exports.default`.
  Configs are data-shaped object literals, so this is fast (<10ms), needs no Node
  round-trip, and works even before `pnpm install`.
  Fallback: if evaluation fails (config uses Node APIs), shell out to the project's own
  Node: `npx tsx <embedded-extractor>.ts <configPath>` → JSON on stdout.
- `SaveSequence(id, def)` — see editing model (§4).

**TemplateService**

- `ListTemplates(sequenceId)` — pairs source files (`src/emails/*.tsx` or any HTML
  source) with rendered output (`build/<id>/templates/*.html`), flags stale/missing
  renders (source mtime > build mtime).
- `RenderPreview(templateKey, sampleData)` — renders the built HTML with Liquid
  variables substituted. Runs the real LiquidJS in goja for exact send-time parity
  (LiquidJS is dependency-free and embeds cleanly); sample data = a synthetic
  subscriber or a real one fetched from DynamoDB.
- `RunRender(sequenceId)` — executes `pnpm --filter <id> render` and streams output.
- `TestSend(templateKey, subject, sender, toEmail)` — one-off SES v2 send of the
  rendered preview to a user-supplied address (guard: only to verified identities
  while SES is in sandbox).

**AwsService** (AWS SDK for Go v2, credentials resolved from `AWS_PROFILE` in `.env`)

- `Whoami()` — STS caller identity + region; shown in the status bar so it's always
  obvious which account the app is pointed at.
- `StackStatus()` — CloudFormation describe-stack + outputs; resource list.
- Subscribers: get by email (`SUB#<email>/PROFILE` + executions + send log +
  suppression), search by tag (`TAG#<tag>` partition), engagement timeline
  (Events table `SUB#` partition).
- Sequences runtime: active execution counts (`EXEC#<id>` partition count), recent
  failed SFN executions, per-sequence counters (`STATS#<id>/COUNTERS`).
- Analytics: Events table `SequenceIndex` / `TemplateIndex` GSI queries for
  time series and per-template (per-variant) breakdowns.
- Broadcasts: list (`BROADCAST` partition) merged with `STATS#<broadcastId>` counters;
  `InvokeBroadcast(input)` with `dryRun` support (mirrors the MCP tool).
- SES: verified identities, sandbox status, send quota, account suppression count.

**DeployService**

- Runs the project's own commands as child processes in the project dir, streaming
  stdout/stderr to the frontend over Wails events: `pnpm build`, `pnpm typecheck`,
  `pnpm synth`, `pnpm run cdk:deploy` (never raw `npx cdk`, per project conventions).
- `Diff()` — `cdk diff` (via the project's dotenv-wrapped script) parsed into a
  structured added/changed/removed resource list.
- Only `Deploy()` and `Teardown()` mutate AWS infra; both require an explicit typed
  confirmation in the UI. Teardown additionally requires typing the stack name.

### 2.2 React frontend

Stays on the scaffolded stack: **React 18 + TypeScript + Tailwind v4 + shadcn/ui**.
Additions:

| Library                 | Purpose                                                                                      |
| ----------------------- | -------------------------------------------------------------------------------------------- |
| `@xyflow/react`         | Sequence flow canvas (view + edit)                                                           |
| `@codemirror/*`         | Template/config editor (much lighter than Monaco — matters for Wails bundle size)            |
| `@tanstack/react-query` | Caching/polling layer over Wails bindings; runtime data polls only while its view is mounted |
| `recharts`              | Analytics charts (funnels, time series)                                                      |
| `react-router`          | Screen routing (memory history)                                                              |

Wails events → a thin event bus that invalidates the relevant react-query keys
(`sequence:changed:<id>` invalidates that sequence + its templates).

## 3. Information architecture & screens

```
Project picker
└── Project shell
    ├── status bar: project path · AWS profile/account/region · stack status · drift badge
    ├── Dashboard
    ├── Sequences
    │   └── Sequence detail (canvas · templates · analytics · subscribers tabs)
    ├── Broadcasts
    ├── Subscribers
    ├── Deploy
    └── Settings (.env)
```

### 3.1 Project picker

First-run screen. Recent projects list + "Open folder…" + "New project" (runs
`npx create-mailshot` with a name prompt, streams output). Opening validates the folder
and surfaces actionable errors ("no `.env` — copy from `.env.example`?",
"dependencies not installed — run `pnpm install`?").

### 3.2 Dashboard

The "is everything okay" screen.

- **Stack card**: CloudFormation status, region/account, last deploy time, drift badge.
- **Sequence cards** (one per local sequence): step count, transactional badge, active
  executions, delivered/open/click counters from `STATS#<id>`, sparkline of last-30-day
  sends, and a "not deployed" state for sequences that exist locally only.
- **Recent activity feed**: latest engagement events across sequences
  (SequenceIndex, newest first) — "j.doe@… opened _day-3-tips_ (onboarding) · 2m ago".
- **Health strip**: SES quota usage, bounce/complaint rate vs SES thresholds
  (warn ≥ 5% bounce / 0.1% complaint), recent failed SFN executions.

### 3.3 Sequence detail — the centerpiece

Header: sequence id, sender identity (from/name/reply-to), transactional/captureReplies
badges, active execution count, Deployed/Modified/Local-only status.

Tabs:

**Flow** — React Flow canvas, auto-laid-out (dagre, vertical):

- Node types: **trigger** (detailType + subscriber mapping), **send** (template name,
  subject; A/B nodes render as a stacked card showing all variants with split
  percentages), **wait** (humanized duration), **choice** (diamond, one edge per
  branch value + default), **condition** (diamond, check description, then/else edges),
  plus side rails for **event emails** (fire-and-forget, dashed border) and
  **exit events**.
- **Stats overlay toggle**: when on, each send node shows delivered/open%/click% pulled
  from `TemplateIndex` — for A/B nodes this is the variant comparison, in place, with
  the leading variant highlighted. This is the single highest-value view in the app:
  the funnel drawn on the flow itself.
- Clicking a node opens the **inspector panel** (right side): all node properties as a
  form (subject, templateKey picker, wait duration, condition fields…). Editing rules
  in §4.
- Canvas edit operations: add step on an edge (+ button on hover), delete step,
  drag to reorder within a branch, convert send → A/B (add variant).

**Templates** — master/detail:

- Left: template list with render status (rendered ✓ / stale ⚠ / missing ✗) and
  usage (which steps reference it).
- Center: tabs for **Preview** / **Source**. Preview renders the built HTML in a
  sandboxed iframe with Liquid variables filled from a sample-data panel
  (editable JSON, or "load real subscriber…"), width toggle (mobile 375 / desktop 640),
  and a raw-HTML view. Source is CodeMirror over the `.tsx`/`.html` source with
  "Render" (runs the project's render script) and "Open in editor" buttons.
- Toolbar: **Send test email** (choose recipient, uses the sequence's sender config).

**Analytics** — per-sequence:

- Step funnel: delivered → opened → clicked per send step, in step order.
- Variant comparison table for any A/B step (sends, open rate, click rate, per variant).
- Time series (events by day, stacked by type) from SequenceIndex.
- Recent failures list (SFN executions with error + input subscriber).

**Subscribers** — who's in this sequence now (`EXEC#<id>` partition): email, started
at, current state (from SFN DescribeExecution on demand), with per-row "stop execution"
(confirmation required).

### 3.4 Broadcasts

- List: subject, sent at, audience size, live delivered/open/click/bounce counters
  (merged from `STATS#<broadcastId>` exactly like the MCP server does).
- Detail: funnel + event time series + the filters that were used.
- **New broadcast** composer: template picker (any built template), subject, sender
  form, filter builder (tags AND attribute equalities) → **Dry run** shows resolved
  audience count → explicit confirm ("Send to 1,204 subscribers") → invoke, then live
  counter view. Dry-run-before-send is enforced by the UI, not optional.

### 3.5 Subscribers (global)

- Lookup by exact email; browse by tag (tag partitions are the only cheap listing path
  — full-table scans are explicitly avoided; state that in the empty state).
- Profile: system flags (unsubscribed / suppressed with reason), custom attributes
  (top-level columns, separated via the same rules as `extractAttributes`), tags,
  active executions, send log, engagement timeline.
- Actions: stop an execution; copy unsubscribe URL. Deliberately **no** "unsuppress" /
  "resubscribe" buttons — those flags are owned by the handlers (framework invariant).

### 3.6 Deploy

A pipeline view mirroring the `/deploy` skill: **Validate → Build → Diff → Deploy**.

- Validate: typecheck + config sanity (unique ids, templates referenced by steps exist
  in build output, sender emails verified in SES — reusing validate-sequence checks).
- Build: `pnpm build`, streamed log with per-sequence collapse.
- Diff: parsed `cdk diff` — resources added/changed/removed, with state-machine changes
  mapped back to "sequence X modified".
- Deploy: disabled until diff has been viewed; typed confirmation; streamed CloudFormation
  events; on success refreshes the Deployed plane and clears the drift badge.
- History: last N deploys (timestamp, duration, outcome) from the local app-data log.
- Teardown lives here too, behind a type-the-stack-name confirmation.

### 3.7 Settings

- `.env` editor as a schema-aware form (keys from `MailshotConfig` + `AWS_PROFILE`),
  with connection test (STS whoami, table exists, bucket exists) per save.
- SES panel: verified identities, sandbox mode warning, quota.
- App prefs: theme, polling intervals.

## 4. Editing model (the hard problem)

`sequence.config.ts` is TypeScript, not JSON — arbitrary code round-tripping is not
feasible. The design embraces a **canonical-shape contract**:

1. On load, the config is evaluated to a JSON `SequenceDefinition` (§2.1).
2. The app **regenerates** the whole file from that JSON using the same code-gen
   template as the `/create-sequence` skill (stable key order, `const id = "…"`,
   template keys derived as `` `${id}/…` ``) and compares it (AST-insensitive:
   compare the _evaluated_ output of the regenerated file to the evaluated original).
3. If they're equivalent → the sequence is **canonical**: full visual editing enabled;
   every save = regenerate file + write. Git remains the safety net, same as skills.
4. If not (hand-written logic, computed values) → **read-only canvas** with an
   "Open config in editor" affordance and inline CodeMirror editing of the raw file.
   No silent destruction of user code, ever.

Template editing is simpler: sources are files; the app edits them directly and runs
the sequence's own render script. The preview always shows _built_ output, so what you
preview is byte-for-byte what deploys to S3.

`.env` edits go through the form only (no free-text), preserving comments where present.

## 5. Safety model

| Action                       | Guard                                           |
| ---------------------------- | ----------------------------------------------- |
| All AWS reads                | none (safe)                                     |
| Save config/template (local) | none — git is the safety net                    |
| Test send                    | recipient confirmation; sandbox-aware           |
| Broadcast                    | mandatory dry run → typed audience confirmation |
| Stop execution               | confirmation dialog                             |
| Deploy                       | diff must be viewed → confirmation              |
| Teardown                     | type the stack name                             |
| Unsuppress / resubscribe     | not offered (framework invariant)               |

The status bar always shows profile/account/region so a wrong-account mistake is
visible before any action.

## 6. Build phasing

**Phase 1 — Read-only project lens** (validates the config-parsing core)
Project picker, `.env` parsing, sequence list + flow canvas (view only),
template preview with Liquid sample data, stack status, whoami status bar.
No AWS writes. Shippable and already useful.

**Phase 2 — Runtime visibility**
Dashboard stats, sequence analytics + stats overlay, subscribers, broadcasts list,
recent failures, health strip. Read-only AWS.

**Phase 3 — Actions**
Deploy pipeline (validate/build/diff/deploy streamed), broadcast composer with dry
run, test send, stop execution.

**Phase 4 — Editing**
Canonical-shape detection, visual step editing + config regeneration, template source
editing + render integration, `.env` form editor, new-sequence wizard (reusing the
create-sequence code-gen).

## 7. Open questions

- **New-sequence wizard vs Claude Code**: the `/create-sequence` skill already does
  this well. Phase 4 could embed a minimal wizard, or the app could simply deep-link
  users to Claude Code for generation and stay a viewer/editor. Leaning: minimal
  wizard for simple linear sequences, Claude Code for anything with branching.
- ~~React Email dev server embed~~ — **resolved: no**. Templates are BYO (React
  Email, MJML, raw HTML, builder exports…), so the app never embeds or assumes any
  template framework. The only editing contract is framework-agnostic: generic code
  editor over the source files + run the sequence's own render script + preview the
  built HTML. Framework-specific tooling stays in the user's own editor/terminal.
- **Multi-project windows**: one project per window (Wails supports multiple windows
  poorly in v2) — likely one project at a time with fast switching.
